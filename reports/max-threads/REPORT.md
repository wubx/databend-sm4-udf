# max_threads 扩展：1–16 线程

**状态：完整测量已结束，所有线程数下的结果校验一致，临时对象已清理。** 单线程对比见 [SM4 三端](../sm4-backends/REPORT.md) 和 [MD5 内置 vs WASM](../md5-native-vs-wasm/rows-100k-1m/REPORT.md)，其他报告见 [报告索引](../README.md)。

## 1. 测试目标与环境

同一条 SQL 只改 `max_threads`，观察内置函数、WASM UDF 和 JS UDF 能否随线程数并行加速，以及加线程后内置与 WASM 的差距如何变化。

- 每个规模单独建表并写成多个数据块；计时 SQL 为 `SELECT count(*), sum(siphash64(expr)) FROM t`，不带 `LIMIT`，让扫描和 UDF 能分给多个线程。单线程报告使用 Memory 表加 `LIMIT`，两者的 SQL 形态不同。
- 每组预热 1 次、正式 3 次，正式顺序用固定种子打乱，取服务端 SQL 耗时中位数。建表、写数据、上传和注册不计时。
- 每次查询的 count 与 checksum 都和预先计算的期望值一致：MD5 对照内置 `md5()`，SM4 解密对照原文；写入前用 WASM 加密，并抽查 257 行确认 WASM 与 JS 解密都还原原文。
- 共 200 次计时查询。JS 只测 1,024 B × 5 万行，单线程约 80 秒。

## 6. 如何解读

- 数据量越大，加线程越有用：每次查询的 WASM 运行时创建和模块编译是固定开销，只发生一次，加线程摊不掉；数据块数少于线程数时，多出的线程也没有活干。
- 内置函数的并行扩展最好，WASM 次之，所以线程越多，内置与 WASM 的耗时比越大。WASM 在 8 线程之后提升变小的原因没有在本测试中定位。
- Databend 每次查询创建一个 WASM 运行时，各线程从同一运行时的实例池中取实例执行（依据本地 Databend 源码）。
- 单机测量，未绑核，最多测到 16 线程；未测并发 QPS、峰值内存或多节点。

## 7. 复现

先构建两个 WASM 工件（见 [README](../../README.md) 与 [MD5 实验说明](../../benchmarks/native-vs-wasm/README.md)），然后在有管理员批准的独立测试实例运行：

```bash
export SM4_URL=http://127.0.0.1:8000
export SM4_USER=root
export SM4_PASSWORD=''
.venv/bin/python benchmarks/max-threads/benchmark.py --threads 1,2,4,8,16 --repeats 3
```

1,024 B × 100 万行约 1 GiB 原文，加上密文列约 2 GiB，请预留存储与内存。自定义 `CARGO_TARGET_DIR` 时用 `--sm4-wasm` / `--md5-wasm` 指定工件。用完整原始记录重新生成本页：

```bash
.venv/bin/python benchmarks/max-threads/report.py --input results/max-threads.json
```

- WASM SHA256：SM4 `19c2c12d50f2b4a3dc9ad1ef1e7cd650b5fe4986b87f829bcfb839a0fee482f7`，MD5 `0d90342bf4926265357099ddf0762b78b0df5025f83eea0080552bd9bebac552`。源码指纹、完整 `EXPLAIN PIPELINE` 和逐次计时见 [results.json](results.json)。
