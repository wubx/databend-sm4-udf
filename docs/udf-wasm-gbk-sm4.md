# Databend 什么时候值得用 Wasm UDF？从 GBK 转码到 SM4 解密

**有合适的内置函数，优先用内置。需要自定义逻辑时，如果报文短、批次小，而且对延迟敏感，先评估 JavaScript UDF；如果要批量处理、每行计算较重，或希望交付编译后的模块，先评估 Wasm UDF。**

GBK 转码实测比较了同一项轻量操作走内置、Wasm 和 Python 的成本；SM4 解密实测则用来回答：没有合适的内置函数时，数据规模如何影响 JS 和 Wasm 的选择？

## GBK 转码：有内置函数，就不必绕一层 UDF

把 Base64 包裹的 GBK 文本转成 UTF-8，在实测的 Databend `v1.2.968-nightly` 上可以直接写：

```sql
SELECT CONVERT_FROM(FROM_BASE64('1tDOxA=='), 'gbk');
-- 中文
```

为了只比较转码，我们把 Base64 解码移出计时路径。三条路径读取同一列 GBK `BINARY` 数据，分别调用内置 `CONVERT_FROM`、Rust/Wasm UDF 和本地 `LANGUAGE python` UDF。Python 使用 `bytes.decode('gbk', errors='strict')`。

| 实现 | 单条 256 B：服务端 P50 | 批量 32 MiB：服务端 P50 | 批量吞吐 |
| --- | ---: | ---: | ---: |
| 内置 `CONVERT_FROM` | **2 ms** | **45 ms** | **711 MiB/s** |
| Rust/Wasm UDF | 92.5 ms | 250 ms | 128 MiB/s |
| 本地 Python UDF | 315 ms | 628 ms | 51 MiB/s |

单条查询只读一行，扫描对照也是 **2 ms**。这份 256 B 的数据很小，Wasm 相比内置多出的约 **91 ms** 是整条查询的额外延迟，并不是这几个字节花了 91 ms 才解码完。到了批量场景，Wasm 的吞吐是本地 Python 的 **2.5 倍**，但内置函数的吞吐仍是 Wasm 的 **5.6 倍**。

**怎么测的：**单连接、单线程，`max_block_size=8192`，关闭结果缓存。输入放在 `MEMORY` 表里，排除对象存储 I/O。批量是 65,536 行合成数据，平均 512 B/行。预热后交错执行，单条每路 24 次，批量每路 7 次。各路通过 `SUM(OCTET_LENGTH(...))` 消费解码结果，只返回一个数字；另行核对每行输出，三路在这批有效输入上逐字节一致。吞吐以输入 GBK 字节数除以服务端耗时计算。

如果是替换已有 Python 转码，还要核对业务所需的字符集语义：这次的内置函数和 Wasm 实现采用 WHATWG GBK，Python strict `gbk` 对部分扩展字节的行为不同。样本一致，不代表任意输入都可直接替换。

## SM4 解密：没有合适的内置函数，再看批次大小

另一组实验来自开源项目 [`databend-sm4-udf`](https://github.com/wubx/databend-sm4-udf)。它把 SM4-CBC 解密封装成 SQL 函数，比较库内 Rust/Wasm、库内 JavaScript，以及通过 Arrow Flight 调用的 Python Server。三路使用相同的输入、接口和兼容规则，并用共享测试向量核对结果。

### 968 补测：固定每行大小，只改变批次行数

在 Databend `v1.2.968-nightly` 上，用同一份仓库快照的 JS 和 Rust/Wasm 实现，走相同的显式 IV 接口。每行固定 **16 B 明文、32 B 密文**，只改变每条 SQL 处理的行数。

| 每条 SQL 的行数 | JS 服务端 P50 | Wasm 服务端 P50 | Wasm / JS 耗时 |
| ---: | ---: | ---: | ---: |
| 1 | **6 ms** | 129.5 ms | 21.6× |
| 100 | **15 ms** | 131.5 ms | 8.8× |
| 1,000 | **99.5 ms** | 132.5 ms | 1.33× |

**怎么测的：**单连接、单线程，使用 `MEMORY` 表，`max_block_size=8192`，关闭结果缓存。密文在计时前准备，逐行核对两路解密结果。每个组合预热一次，再交错执行 12 次正式测量。每条计时 SQL 对输出做哈希聚合并核对结果；表中是整条查询的服务端耗时，不是纯算法耗时。

从 1 行到 1,000 行，Wasm 的中位耗时只增加 **3 ms**，JS 从 **6 ms** 增到 **99.5 ms**。这个趋势表明，Wasm 在短查询里的固定开销占比较高，但本轮没有拆分各项开销。**测到的三个规模都是 JS 更快，本轮没有测到 Wasm 反超的批次大小。** 不要把 1,000 行当作通用的选型阈值。

### 947 历史测试：较重的批量解密中，Wasm 明显领先

以下是 [SM4 性能矩阵](https://github.com/wubx/databend-sm4-udf/blob/14c7b8e3b602a3fd0b1855455a25860b2a7cae33/reports/sm4-backends/REPORT.md) 中的两个规模，来自另一轮 Databend `v1.2.947-nightly` 测试。表内是单线程服务端 SQL 耗时中位数：

| 单次 SQL 的处理规模（按明文计） | Wasm | JavaScript | Python Server |
| --- | ---: | ---: | ---: |
| 16 B × 1,000 行 | 147 ms | **108 ms** | 205 ms |
| 1 KiB × 50,000 行 | **0.611 s** | 80.260 s | 169.016 s |

历史测试中，短报文的小批次同样是 JS 更快；处理 50,000 条 1 KiB 记录时，Wasm 明显领先。这个结果说明较重的批量任务值得测 Wasm，但不能和 968 的三个点拼成同一条曲线：测试版本不同，大批量用例也同时增加了行数和每行字节数。

历史测试中的 Python 使用独立的 Arrow Flight 服务和 `gmssl`，不是 GBK 实验里的本地 Python UDF。Rust、JavaScript 和 Python 的 SM4 实现也不同。表里的差距是**这几套具体实现的完整 SQL 性能差异**，不能全归因于运行时，也不能用来预测其他算法的加速倍数。

## 怎么选：内置、JS 还是 Wasm？

| 你的场景 | 建议 |
| --- | --- |
| 已有满足语义的内置函数，例如 GBK 转码 | **直接用内置。** 不必为相同功能额外维护模块或承担 UDF 调用开销。 |
| 没有内置函数，单次 SQL 处理的记录少、报文短，且对延迟敏感 | **先评估 JS。** 用实际行宽和批次大小测 P50/P95，不照搬 SM4 的行数。 |
| 没有内置函数，要在导入、清洗或回填时批量处理自定义报文、编解码或加解密，或每行计算较重 | **先评估 Wasm。** 用实际行宽、批次大小和并发测吞吐与延迟，同时核对输出和失败行为。 |
| 希望在库内运行自己的实现，但只交付编译产物，不交付源码 | **评估 Wasm 模块交付。** 将实现编译成 `.wasm`，保留稳定的 SQL 函数接口。 |
| 已有成熟 Python 实现，依赖 Python 生态，调用量也不高 | **可以先保留 Python。** 出现明确的延迟或吞吐瓶颈，再评估是否值得迁移。 |

Wasm 还有一个交付上的好处：**客户可以在自己的代码仓库维护源码，只交付编译后的 `.wasm`。** 在支持并启用了 Wasm UDF 的实例上，将模块上传到受控 Stage，注册函数时引用模块；调用方只需要了解输入、输出和错误约定，不必在 SQL 或函数 DDL 里贴出业务源码。如果只是不想在 DDL 里内联代码，JS 也可以引用 Stage 上的脚本；Wasm 的区别是部署时交付的是编译产物，而不是源码。实操可以参考 [Wasm 部署指南](https://github.com/wubx/databend-sm4-udf/blob/14c7b8e3b602a3fd0b1855455a25860b2a7cae33/docs/DEPLOY_WASM.md)。

**不交付源码，不等于模块保密。** 能读取 `.wasm` 的人仍可分析它，生产密钥不应写进模块或 SQL 字面量，应通过单独的密钥管理方案处理。文中的 SM4 项目用于互操作和性能验证，未经密码学安全审计；CBC 不提供完整性认证，不应把示例直接用于设计新的加密协议。详见[项目安全说明](https://github.com/wubx/databend-sm4-udf/blob/14c7b8e3b602a3fd0b1855455a25860b2a7cae33/SECURITY.md)。

做选型时，用同一段业务逻辑测三个数：**单条延迟、典型批次吞吐、最大批次耗时**。如果主要跑短小的在线请求，先看 JS 能否满足延迟目标；如果主要跑批量任务，或需要交付编译模块，就看 Wasm 能否在实际批次上达到吞吐和延迟要求。
